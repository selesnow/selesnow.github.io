# Коммит и пуш

Сайт живёт в `master`, GitHub Pages публикует его после пуша. Пуш = публикация для всех, поэтому он делается только по
просьбе пользователя (разрешение на один пуш не распространяется на следующие). Отдельная сложность: GitHub Actions
(`update-stats.yml`) каждый день в 06:00 UTC и при пуше в `_blog/**` коммитит в `master` пересобранные страницы и счётчики,
так что локальная копия почти всегда отстаёт.

## Порядок

1. **Осмотри**: `git status --short` и `git diff --stat | tail`. Коротко реши, из чего состоят изменения: правка шаблонов,
   данные, статья блога, фото, сгенерированные страницы. Предупреди об «посторонних» файлах (например, `assets/acpgram-stats.json`
   меняется сам при каждой сборке: это нормально, он идёт в коммит вместе с остальным).
2. **Подтяни**: `git pull --rebase --autostash`. При конфликте не разрешай вслепую:
   - счётчики и сгенерированные страницы (`assets/stats.json`, `_build/data/package_stats.json`, `blog/`, `courses/` и т. д.):
     возьми версию удалённого репозитория и пересобери `python _build/build.py`;
   - остальные файлы: остановись и спроси пользователя.
3. **Если менял шаблоны, стили или данные — пересобери** (`python _build/build.py`) до коммита, иначе в репозитории окажутся
   устаревшие страницы или `tailwind.css` без нужных классов. Для визуальных правок сначала прогони скилл `site-check`.
4. **Набери файлы осознанно.** Обычно `git add -A` годится: в репозитории всё лишнее исключено, но проверь `git status`:
   - не должно попасть: `_blog_export/` (исходники и 71 МБ оригиналов картинок), временные скриншоты, `.env`/ключи;
   - если в рабочей копии лежат две несвязанные работы (например, статья и правка шаблона), предложи разделить на два коммита.
5. **Сообщение коммита** в стиле истории репозитория (`git log --oneline -10`): `тип(область): суть`, типы `feat`, `fix`, `chore`, `docs`,
   затем 2–4 строки-пункта о том, что изменилось и зачем. Английский, как в существующих коммитах. Добавь строку атрибуции, которую
   задаёт окружение. Сообщение передавай через несколько `-m` или heredoc: в Git Bash многострочные кавычки легко ломаются.
6. **Запушь**: `git push`. Вывод предупреждений про CRLF огромен, режь его через `| tail -3`.
7. **Проверь результат**:
   - `git fetch -q; git rev-parse HEAD origin/master` — хэши совпадают;
   - если изменился `_blog/**`, запустится workflow и сам добавит коммит со сборкой: перед следующей работой нужен `git pull`;
   - если установлен `gh`: `gh run list --limit 3` — workflow `Update package stats` должен завершиться успешно;
   - Pages обычно выкладывают за 1–2 минуты; при жалобе «не обновилось» посоветуй Ctrl+F5.
8. **Доложи**: хэш и тему коммита, что вошло, что осталось неотправленным (если что-то осталось).

## Чего не делать

- Не пушь с `--force`, не используй `--no-verify`, не переписывай уже опубликованную историю.
- Не коммить `_blog_export/` и не добавляй `.agents/` (это локальная ссылка на скиллы, она исключена в `.git/info/exclude`).
- Не меняй `git config` пользователя.
- Не разрешай конфликты в авторских файлах (тексты статей, `index.html`) без вопроса.

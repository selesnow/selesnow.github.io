# alexey-seleznev.pro

Личный сайт Алексея Селезнёва (GitHub Pages, ветка `master`, домен из `CNAME`).

## ⚠️ Перед началом любой работы — `git pull`

GitHub Actions (`.github/workflows/update-stats.yml`) каждый день в 06:00 UTC коммитит
в `master` свежие счётчики скачиваний и звёзд и пересобирает страницы. Поэтому локальная копия
почти всегда отстаёт от удалённой.

1. Первым делом выполни `git pull` (при незакоммиченных изменениях — `git pull --rebase --autostash`).
2. Если pull завершился конфликтом, не разрешай его вслепую: в файлах счётчиков
   (`assets/stats.json`, `_build/data/package_stats.json`, сгенерированные страницы) бери версию
   с удалённого репозитория и пересобирай страницы, а в остальных файлах сначала спроси пользователя.
3. Коммить и пушь только по просьбе пользователя.

## Устройство проекта

- `index.html` — одностраничный лендинг. **Правится только вручную**, генератор его не трогает.
  Пользователю лендинг очень нравится: меняй в нём только то, о чём просят.
- Внутренние страницы `opensource/`, `courses/`, `videos/`, `talks/`, `articles/`, `interviews/`
  (`index.html` в каждой) **генерируются** скриптом `_build/build.py` из JSON в `_build/data/`.
  Не правь их HTML руками — изменения пропадут при следующей сборке (в том числе ночной).
  Меняй данные в `_build/data/*.json` или шаблоны в `_build/build.py`, затем запускай
  `python _build/build.py`.
- `blog/` — **блог, генерируется** `_build/blog.py` (его вызывает `build.py`) из Markdown в `_blog/posts/*.md`.
  Не правь `blog/*/index.html` руками. Новая статья = файл в `_blog/posts/` + пуш: workflow `update-stats` собирает блог при
  пуше в `_blog/**` и ночью. Инструкция по шапке, тегам, картинкам и обложкам — `_blog/README.md`.
  Опубликованные картинки лежат в `blog/images/` (в git, сборка их не очищает); новые клади в `_blog/images/`, сборка сама сделает WebP.
  `slug` статьи задаётся в шапке и **не меняется** (это адрес). Имена файлов — только короткая латиница: длинные кириллические имена
  (>255 байт) ломают клонирование на Linux. `build.py` сам обновляет в `sitemap.xml` блок `/blog/`.
  Исходники миграции с WordPress — `_blog/migration/` (для истории); `_blog_export/` (сырые данные, оригиналы картинок) исключён из git локально.
  Раздел «Статьи» (`articles/`) — только **внешние** публикации; свои заметки живут в блоге.
  Если оригинал внешней публикации пропал, ссылка ведёт на снимок в Web Archive (`"via": "archive"`, бейдж «из архива»), а не на копию в блоге.
- `ads/index.html` — страница о рекламе в Telegram-канале R4marketing (`build_ads()`, данные в `_build/data/ads.json`).
  **Ссылок на неё с сайта нет и в sitemap её не добавлять** — она открывается только по прямой ссылке.
- `404.html` в корне тоже генерируется (`build_404()`). GitHub Pages отдаёт её по любому несуществующему
  адресу, в том числе вложенному, поэтому все пути на ней абсолютные (`/assets/...`, `/courses/`).
- `_build/` не публикуется: Jekyll игнорирует каталоги, начинающиеся с `_`.
- `_worker/acpgram-docs-chat/` — Cloudflare Worker для AI-чата на странице справки AcpGram (`/acpgram/docs/`), тоже не публикуется.
  Деплоится отдельно (`npx wrangler deploy` из его каталога) и только по просьбе пользователя; ключ OpenRouter — секрет воркера,
  в репозиторий и в код страницы не попадает. Текст справки воркер берёт с сайта (`acpgram/docs/docs.<lang>.txt`, пишет сборка),
  поэтому после правки справки передеплой не нужен. Подробности — `README.md` воркера и `_build/ACPGRAM.md`.
- `assets/site.css`, `assets/site.js` — общие стили и скрипт внутренних страниц;
  стили повторяют лендинг (Tailwind CDN, bento-glass карточки, фон Vanta.js).
- `assets/stats.json` — публичный снимок счётчиков (cranlogs + GitHub API), его читают лендинг
  и `/opensource/`. Обновляется ночным workflow или командой `python _build/build.py --stats-only`.
- `assets/logos/` — логотипы пакетов, `assets/services/` — обложки сервисов.
- `assets/photos/` — фото с конференций для шапок разделов (WebP, сжатые копии исходников из `img/`).
  Какое фото в каком разделе, подпись и кадрирование (`pos`) задаются в `PHOTOS` в `_build/build.py`.
- Остальные каталоги в корне (`r4excel_users/`, `rfacebookstat/` и др.) — старые проекты, не трогать.

## Правила контента

- Весь видимый текст трёхъязычный: `<span class="ru-text">…</span><span class="ua-text">…</span><span class="en-text">…</span>`.
  В генераторе для этого функции `T(ru, ua, en)` и `tr({...})`. Язык хранится в `localStorage.preferredLang`.
- Ссылки на курсы и документацию пакетов — через домен `https://alexey-seleznev.pro/...`, не `selesnow.github.io`.
- Битые внешние ссылки на статьи/интервью заменяй снимком оригинала в Web Archive (`https://web.archive.org/web/<дата>/<исходный URL>`,
  карточка помечается `"via": "archive"`): это подтверждение, что публикация была. Оригинальные адреса бери из старого списка
  https://alexey-seleznev.pro/publications/, наличие снимка проверяй API `https://archive.org/wayback/available?url=…&timestamp=ГГГГММ`
  (прямые запросы к web.archive.org с этой машины блокируются как бот-трафик). Старый WordPress-блог (alexeyseleznev.wordpress.com)
  как замену больше не используем — копии лежат в `/blog/`. Нет снимка — не публикуй мёртвую ссылку, сообщи пользователю.
- Пакеты ryandexdirect, rym, rvkstat, rmytarget помечены как архивные (`"archived": true`);
  пояснений о причинах архивации на сайте быть не должно.
- Футер общий для всего сайта: шаблон `footer(prefix)` в `_build/build.py` (колонки «Сайт»,
  «R4marketing и публикации», «Контакты»). Колонка «Сайт» строится из списка `PAGES`.
  На лендинге стоит вывод `footer('')`: после изменения шаблона замени блок `<!-- FOOTER -->`…`</footer>`
  в `index.html` (`python -c "import sys; sys.path.insert(0,'_build'); import build; print(build.footer(''))"`).
- Новую внутреннюю страницу добавляй в `PAGES`, в `sitemap.xml` и обновляй футер лендинга.

## Стили, аналитика, SEO

- **Tailwind собирается заранее**, CDN не используется. `assets/tailwind.css` строится из классов, найденных
  в HTML-страницах, `assets/site.js` и `_build/build.py` (см. `_build/tailwind.config.js`).
  **Если добавил новый Tailwind-класс** (в `index.html`, шаблоны или JS) — запусти `python _build/build.py`
  (нужен Node.js/npx), иначе у класса не будет стилей. Ночной workflow тоже пересобирает CSS.
  `tailwind.css` подключается последним в `<head>` (как это делал CDN) — порядок не менять.
- Шрифты Inter и Outfit подключаются тегом `<link>` в `<head>` (с `preconnect`), не через `@import`.
- **Google Analytics 4:** ресурс `G-Z56YHE916N`, идентификатор в `GA_ID` в `_build/build.py`
  (пусто — счётчик не подключается). Сайты курсов (отдельные репозитории) подключены старым тегом
  `UA-114798296-1`; Google связал его с этим же GA4-ресурсом, так что их данные тоже попадают в `G-Z56YHE916N`.
  На лендинге сниппет `gtag.js` вставлен вручную в `<head>` — при смене ID поменяй в обоих местах.
- **Структурированные данные (schema.org JSON-LD)** не отображаются на странице. Лендинг: Person + WebSite
  (вывод `build.landing_jsonld()`), внутренние страницы: CollectionPage, для курсов — список Course,
  для пакетов — SoftwareSourceCode. Данные о человеке — в `PERSON` в `_build/build.py`; после изменения
  обнови блок `application/ld+json` в `index.html`.
- **Язык:** явный выбор кнопкой EN/RU/UA хранится в `localStorage.preferredLang`; без него язык берётся
  из настроек браузера (uk → UA, ru → RU), иначе EN. Автоопределение не сохраняется.
- `sitemap.xml` правится вручную: страницы сайта, сайты курсов на этом домене (отдельные репозитории),
  `publications/`. Проверяй, что все адреса отдают 200.

## Аналитика сайта: Search Console и GA4

Эффективность сайта оцениваем по реальным данным, а не по догадкам. Для этого есть два навыка со скриптами (`.claude/skills/gsc-data/`, `.claude/skills/ga4-data/`;
агентам без поддержки навыков — запускать скрипты напрямую). Они читают данные через сервисный аккаунт и **только читают**: изменить Search Console или GA4 они не могут.

```
python .claude/skills/gsc-data/scripts/gsc.py sites | query | sitemaps | inspect URL
python .claude/skills/ga4-data/scripts/ga4.py properties | preset NAME | report --dims … --metrics …
```

- **Search Console** (`gsc.py`): клики, показы, CTR и позиция по запросам, страницам, странам, устройствам и дням; проверка индексации URL (`inspect`: индексирован ли,
  какой canonical выбрал Google, когда обходил); состояние sitemap. Ресурс `sc-domain:alexey-seleznev.pro`. Данные запаздывают на 2–3 дня.
- **GA4** (`ga4.py`): сессии и пользователи по странам, языкам браузера, каналам, источникам, посадочным страницам; отдельный отчёт `preset ai` — переходы из AI-ассистентов
  (ChatGPT, Perplexity, Claude, Gemini и др.). ID ресурса — `282495698` (`--property` или переменная `GA4_PROPERTY`).
- **Для чего это нужно:** оценивать SEO-правки (title, description, превью, `llms.txt`), следить за индексацией блога, решать вопросы с языками сайта,
  видеть AI-трафик, находить страницы с показами без кликов и позиции 8–20. Любой совет по SEO подкрепляй этими данными.
- **Точка отсчёта на 21.11.2026** (для сравнения после правок): Search Console за 90 дней — 2 клика, 192 показа, средняя позиция 10,3; GA4 за 90 дней — Organic Search 787 сессий
  (Google 186), AI Assistant 3 сессии; языки: русский 1091 сессия, английский 949. Трафик из США, Сингапура и Китая с вовлечённостью около 10–15% похож на ботов — смотри его отдельно.
- **Доступ и секреты:** ключ сервисного аккаунта лежит вне репозитория: `~/.config/seo-access/service-account.json` (или `$GOOGLE_SA_KEY`); нужны `pip install google-auth requests`.
  **Ключи, токены, выгрузки CSV и дашборды с данными аналитики не клади в репозиторий и не коммить**: сайт публичный. CSV сохраняй вне репо (`--csv`).
  Инструкция по настройке — в `.claude/skills/gsc-data/SKILL.md`.
- Навыки `ai-seo` и `seo-audit` в `.claude/skills/` — сторонние, в git не попадают (`.gitignore`); `gsc-data` и `ga4-data` — наши, в git лежат.

### Старый блог на WordPress.com

Старый блог `alexeyseleznev.wordpress.com` оставлен намеренно: на бесплатном тарифе нельзя настроить редиректы, а удаление дало бы 404 на все старые внешние ссылки.
Через WordPress.com REST API (скрипт `_blog/migration/wp_notice.py`, токен — `~/.config/seo-access/wpcom_token.json`, вне репозитория) во всех 146 записях добавлена плашка
со ссылкой на новую версию `/blog/<slug>/`, а на главной закреплена запись «Блог переехал». Плашка помечена комментарием `<!-- moved-notice -->`, повторный запуск её не дублирует.
Перед правкой оригинал каждой записи сохранён в `~/.config/seo-access/wp-backups/<ID>.json`; откат — `wp_notice.py --restore ID|all`. Соответствие «старая запись → новая статья»
берётся из `original_url` и `slug` в шапках `_blog/posts/*.md`. Любые правки на этом внешнем сайте — только по просьбе пользователя и сначала сухим прогоном (запуск без аргументов).

## Проверка

Локальный сервер: `python -m http.server 8765` из корня репозитория (YouTube-плеер на `file://` не работает).
Скриншоты: headless Chrome с `--screenshot`; у headless-режима минимальная ширина окна около 500px,
поэтому мобильная обрезка на скриншотах — артефакт, а не баг вёрстки.
